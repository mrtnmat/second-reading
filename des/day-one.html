Day one: a running game and a plan

Demon's Souls, the journal, part 1 · revised 2026-11-04 · draft

In short

We started on Demon's Souls with no goal beyond "an investigation".

Within ninety minutes the game was running natively on a PC, thanks to work the community had already done. By the end of the evening we had picked a target: just the first boss, the Vanguard, rebuilt as a small simulation.

Reading the game's data and code went fast. That speed is part of why the next night came as such a shock.

How it went

"Leverage what's already there"

The owner (the person who runs this workspace) opened the project at 17:11 with a list of community resources and one rule: lean on them.

That list changed everything. It held:

  • two recompilation projects for Demon's Souls, by JonathanDC64 and by timboat, both built on the general PS3 recompiler ps3recomp;
  • the modding tools Paramdex, Soulstruct, SoulsFormatsNEXT and DSMapStudio, which already read most of the game's files.

What a recompiled port is

A recompiled port is the game's own program, translated function by function from PlayStation 3 machine code into C, then compiled for a PC. This is called static recompilation.

No emulator runs underneath. The game simply is a PC program now.

For us, that meant the game was suddenly a C program we could build ourselves. All of its roughly 94,000 functions were there as C source. They are machine-made, nameless and very hard to read, but they are there.

Why is a PlayStation 3 game so hard to take apart?

A game program is a long list of tiny instructions for one specific processor: "add these two numbers", "fetch this value from memory", "jump over there". Nobody writes those by hand. Programmers write readable source code, and a compiler turns it into instructions. The source code stays at the studio.

The PlayStation 3 makes things harder than most consoles. Its processor, the Cell, has one main core plus six smaller helper cores available to games, that run their own little programs side by side. On top of that sit a separate graphics chip and Sony's own system libraries. A PS3 game is written for all of that at once.

Decompiling and recompiling

Both start from the same instructions, but they aim at different things.

Decompiling turns the instructions back into source code that a person can read and understand. It is slow, careful work, done one piece of the program at a time.

Recompiling translates the instructions mechanically into source code for a different machine, so the game can run there. Nobody has to understand it. The result works, but it reads like a phone book: thousands of functions called func_002FB840 and so on.

The community had done the recompiling. Our job is closer to the decompiling: working out what those nameless functions mean.

"I got killed by Vanguard"

We built timboat's port. At 18:42 the owner reported back:

I got killed by Vanguard :(

That is what is supposed to happen; most players lose that fight. It also meant the build worked: the owner had played through the whole tutorial.

They noted real glitches too. A backstab was cancelled halfway, and the level visibly loaded piece by piece. The notes record both as unexplained.

A first look inside

A quick survey of the program followed, and it brought good news and bad news.

The good news: much of the game's behaviour isn't in the program at all.

  • Enemy AI and map events ship on the disc as 272 readable Lua scripts, comments in Japanese included.
  • The program hands about 1,100 of its functions to those scripts by name, so part of its code comes with real names.

The bad news: the size.

  • By our estimate, the game's own code is 25,000–30,000 functions, 50 to 100 times a PlayStation 1 game.
  • On top of that sit the bought-in physics engine Havok and Sony's system libraries.

What is a script, and why does it help?

Many games are built in two layers. The heavy machinery (drawing, physics, sound) is compiled into the program. The decisions ("if the player is close, swing the club") are written in a small, simple language that the program reads from files while it runs. Those files are scripts.

Scripts are a gift to researchers. They ship on the disc as plain text, often with the developers' own comments left in. And whenever a script asks the program to do something, it has to ask for it by name: GetDist, SetSuperArmor, RevivePlayer. Each of those names labels a piece of the otherwise nameless program.

Demon's Souls uses the language Lua for its scripts.

One boss, nothing else

At 18:54 the owner set the direction:

I would just not consider most of the game until we are happy with one interesting situation, like a single boss fight.

The Vanguard was the obvious pick. It is one enemy in a small arena, with no phases, right at the start of the game.

The game's own files call it デブデーモン, "Fat Demon". The owner's reaction, a few minutes later:

DEBU DEMON, omg too good

we don't even need the stage, just debu demon on a flat world and a character that does nothing but move

What is a headless simulation?

A game does two jobs at once. It simulates: it works out where everyone is, who hits whom, how much health is left. And it presents: it draws the picture and plays the sound.

A headless simulation keeps only the first job. There is no picture, just numbers going in (the player's controller input) and numbers coming out (positions, attacks, damage). That makes it fast, so it can run thousands of fights in a minute, and easy to check, because every number can be compared with the real game's.

We had built one before, for an arcade shooter. The plan was to do the same for a single boss fight.

Three fast hours

The next three hours went fast, because almost all of it was reading:

  • The Vanguard's brain is one 6 KB Lua script. Each time it acts, it picks one of five attacks by weighted chance.
  • Its attacks' timings and hit shapes came out of the animation files.
  • The native routines under the script were decompiled, all the way down to the virtual control stick the AI "pushes" to walk.

The odds aren't what the script says

One small find from that evening is our favourite.

The script gives each attack a weight. But the close attack is tested against one random roll, and the other four against a second, separate roll. So the real odds differ from the weights in the code.

Up close, the sweep attack comes up 32 % of the time, although the script gives it a weight of 20. The full table is below.

A port would keep the real odds, since that is how the game has always played.

Weights, rolls, and why two rolls change the odds

A "weighted" choice works like a raffle. Give the sweep 20 tickets, the close hit 60, the others 10 each: 100 tickets in all. Draw one ticket, and the sweep wins 20 times in 100. One draw decides everything.

The Vanguard's script draws twice. The first draw only asks "close hit, yes or no?". If the answer is no, a second, fresh draw picks among the rest, but it still counts the close hit's tickets, and those happen to fall to the sweep.

It looks like a slip, and one draw was probably meant our reading. The two-draw version quietly favours the sweep up close. Nobody playing could have measured that exactly; the code shows it directly.

From here on it gets technical: formulas, memory addresses and how each claim was checked.
