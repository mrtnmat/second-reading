The first three days

Demon's Souls, the journal, part 1 · revised 2026-11-04 · draft

In short

On the evening of 2 November 2026 we started on Demon's Souls with no goal beyond "an investigation". Other people had already done the hardest part. Two community projects had turned the PS3 program into a native PC program through static recompilation, and the modding community had decoded most of the game's file formats. Within ninety minutes, a recompiled build was running on our machine and the owner (the person who runs this workspace) had died to the first boss, the Vanguard.

The first plan was small and concrete: rebuild just the Vanguard fight as a headless simulation, the way we had done for an arcade shooter before. Reading the game's data and code went fast. Testing against the running game went very slowly, one question per run and nearly a minute of loading each time. At five in the morning the owner gave two options: find a way to manipulate the game, or cancel the whole project.

We found the way. Then the goal changed. The owner dropped the boss-fight simulation and set a bigger target: understand the game well enough to reproduce its systems one by one in our own code, without the PlayStation underneath. The approach became "pick something easy to test in the game, take it apart, measure how sure we are, then move on". Starting with the physics engine, everyone's least favourite part, this approach worked. A day and a half later, one movement step of the player could be computed entirely by our own code, matching the game bit for bit on the recordings we had.

How it went

Day one, evening: a running game in ninety minutes

The owner opened the project at 17:11 with a list of community resources and one rule: lean on them. That list changed everything. It held two recompilation projects for Demon's Souls (by JonathanDC64 and by timboat) built on the general PS3 recompiler ps3recomp, plus the modding tools Paramdex, Soulstruct, SoulsFormatsNEXT and DSMapStudio.

A recompiled port is the game's own program, translated function by function from PlayStation 3 machine code into C and compiled for a PC. No emulator runs underneath. For us, that meant the game was suddenly a C program we could build ourselves, with all of its roughly 94,000 functions as C source. Those functions are unreadable, machine-made and nameless, but they are there.

We built timboat's port. At 18:42 the owner reported back: "I got killed by Vanguard." They had played through the whole tutorial, so the build worked. They also noted real glitches (a backstab cancelled halfway, the level visibly loading piece by piece), and the notes record them as unexplained.

A quick survey of the program followed. The good news was that much of the game's behaviour isn't in the program at all. Enemy AI and map events ship on the disc as 272 readable Lua scripts, comments in Japanese included. The program hands about 1,100 functions to those scripts by name, so part of its code comes with real names. The bad news was the size. By our estimate, the game's own code is 25,000–30,000 functions, 50 to 100 times a PlayStation 1 game. On top of that come the bought-in physics engine Havok and Sony's system libraries.

The first plan: one boss, headless

At 18:54 the owner set the direction: "I would just not consider most of the game until we are happy with one interesting situation, like a single boss fight." The Vanguard was the obvious pick: one enemy, a small arena, no phases, right at the start of the game. The owner added a few minutes later: "we don't even need the stage, just debu demon on a flat world and a character that does nothing but move." (The game's own files call the Vanguard デブデーモン, "Fat Demon".)

The next three hours went fast, because almost all of it was reading. The Vanguard's brain is one 6 KB Lua script that picks one of five attacks by weighted chance. Its attacks' timings and hit shapes came out of the animation files, and the native routines under the script were decompiled down to the virtual control stick the AI pushes to walk.

One small find from that evening is our favourite. The script's weights aren't the real odds. The close attack is tested against one random roll and the other four against a second, separate roll. So up close, the sweep attack comes up 32 % of the time although the script gives it a weight of 20 in the code. A port would keep the real odds, since that is how the game has always played.

The night: watching from outside

Reading only gets you so far. To check anything, we had to watch the real game run. The tools built that night were each reasonable on their own: a watch that reports when the game reads a chosen memory field, a way to run the game without a window and feed it controller input from a file, a patch to skip the boot logos, and finally a live channel for reading, writing and freezing memory while the game runs.

Each run, though, spent about 45 seconds booting and loading a save before it could answer one small question. The tutorial has no save points of its own, so getting anywhere near the boss took several minutes. The first enemy we picked to study never attacked at all, however provoked. The owner checked that in their own play, and it was simply that kind of enemy. Hardware trouble that night forced every run and build to be throttled too.

At 02:48 the owner asked how this was expected to go. The honest answer was "weeks". Five minutes later: "I think the approach is wrong." And then the point that set the course for everything after: "to me it is absurd that this is proceeding slower than full black box decomp work we've done using emulators."

They were right. We had been treating a C program we compile ourselves as if it were a sealed console, watching memory one field at a time. Within the hour the build had a symbol file, so an ordinary Windows debugger could stop inside any game function by name. Then the owner suggested the step that mattered most: "we need to load a custom dll with the game, so we have a hook to load our code without recompiling every time." A full game build takes a long time, and from then on each one needed the owner's approval. Plugins needed neither. The first plugin unlocked the game's own hidden debug menu, and that menu can start the Vanguard's map directly, with no save at all.

Five in the morning: manipulate it, or cancel

The next hour taught a lesson about who knows what. We spent it trying to understand how saving works, and how close you must get before the Vanguard wakes up. The owner knew both answers from playing: saves always put you back at the start of the area, and bosses have no wake-up range, because the fight starts when you walk through the fog gate. "Why don't you just ask me? We just went on a multi-hour quest for info I can get you in 2 seconds flat." That has been a standing rule since: facts about how the game behaves come from the player first, and only mechanisms are traced.

The simulation got built anyway, with every unchecked value named as a stand-in for later tuning. Its attack choices matched the real odds from the code within about half a percentage point. Then, at 05:01: "If it's headless, what use is it to me?" At 05:06: "Two options: we find a way to manipulate the game, or we cancel the whole project."

The obvious way to manipulate it, teleporting the player, had failed earlier. Long jumps had left the player stuck in fog, presumably because that part of the map hadn't loaded. The owner didn't accept the guess: "try warping around the map, test well, make sure the problem we imagine is actually there, or isn't. Then we'll call the shots." The test took four minutes. Starting from the debug menu instead of a save, four long jumps across the Vanguard's map all landed cleanly. The last one went straight into the arena, with the boss's health bar on screen and the player already knocked down. The fight was now reachable in about a minute, on demand.

The new goal

At 05:16 the owner changed the target. In short: they didn't care about the simulation, which they had only picked because it seemed easy. "We eventually want to be able to reproduce all its functionalities one by one instead of running the original code through a translation layer." And: "Where do we start? What gives you leverage?"

The goal was written into the project's instructions within ten minutes: reproduce the game piece by piece without the PlayStation's concepts. The first task was to find out how hard that would be. Two quick measurements followed. A static pass looked for clean boundaries between the program's modules, and a CPU sample of the Vanguard fight showed where the time goes. Neither gave a simple answer, and a later pass corrected the first sample's labels.

So the owner narrowed it again, this time to one system, chosen for being hard: "What can we know about Havok itself? How does it work internally?" And then: "I can be fine with a VERY VERY VERY long process, as long as the intermediate steps are meaningful and interesting. I don't really care about easy results, I want to build a powerful machine to tear down this physics engine piece by piece." The method was to pick what is easy to test in the game first, and branch out from there.

Day two: the physics engine, piece by piece

That morning made the case for the new approach. By 07:00 the program's own type information gave us the layouts of 366 Havok classes and names or tags for 5,955 of Havok's functions. We found the routine that moves a character, and the first experiment (walking into a wall) showed the engine removing the part of the velocity that points into the wall, as theory says it should. Underneath it, the game itself lifts the character 30 cm, lets Havok move it, then snaps it back down to the floor with its own check. A second session started mapping FromSoftware's own engine, Dantelion: 4,910 classes by the end of the morning.

The owner put the old way of working in one sentence: "the idea that you weren't sure about the function despite having access to the decomp still blows my mind."

The afternoon brought a mistake that both sides had made. We planned to study the running jump, and the owner had trouble with it in their own play too. Then an outside answer arrived: the 2009 game has no manual jump at all. "It's particularly hilarious because we evidently both made the same mistake."

The owner started playing with a logging plugin running, dropping off ledges and stairs on purpose so the recordings held real falls. The falls held a surprise: the player fell at half the expected rate. The first suspect was the port's 60 frames per second, so research moved to the game's original 30, and has stayed there since. Eight minutes later that was corrected: the falls were just as slow at 30. The cause was in the game's own code, which builds each frame's fall from the velocity of two frames earlier. The owner also noticed something in the log that no player sees: every play begins with the character falling 1.2 metres. An extra character on an otherwise unused collision layer got the owner's guess first, a scripted version of the ghosts that show other players' play. The game's class name agreed: ReplayGhostIns. Soon after, our model of Havok's collision response matched 213 of 214 recorded frames.

By then several sessions were working at once, on physics, on the Dantelion map, on the collision world and later on sound. They shared one running copy of the game and took turns, with the owner passing written plans and notes between them.

"How hard it is to be sure how right we are"

At 16:59 the owner stated the principle the rest of the work runs on: "It's not just how hard it is to get everything right, but how hard it is to be sure how right we are. If there is a complex but relatively isolable system, we can stub one and be sure we know we are stubbing a fake implementation in. What we want to avoid are hard-to-track divergences."

The next assignment followed from it: reproduce one movement step of the player independently, in three levels. First take Havok's own contacts as given and compute the response. Then compute the contacts ourselves from our own map of the collision world. Finally compute the whole step. Every value had to be labelled as ours, supplied from the game, deliberately faked, approximate or not yet understood. For every mismatch, we had to find the earliest wrong number. "The real success criterion is not that the player moves. It's that we can distinguish faithful reproduction from approximation, and know exactly where our understanding ends."

The night of day two: bit for bit

Through the night, one Havok routine after another was written out by hand and checked against the game, each with an exact score: the ground check, the walk through Havok's compressed collision tree (22,500 of 22,500 steps identical), the constraint solver, and the closest point between the character's capsule and a triangle. At 01:10 on 4 November came the milestone: on the recorded walks, a full movement step with all collision computed by our own code, bit for bit equal to the game measured. By morning, the code that chooses the walking animation and its turns ran in a closed loop with that physics step. The 180-degree turn was reproduced too.

The owner set one more rule that night. A simulation may take outside events from a recording, but only on the frame they really happened, and labelled as such: "That makes the difference between a causal simulation with known external events and a replay that has advance knowledge."

Day three: back to the Vanguard, from below

By the morning of the third day, the work had returned to the boss, this time from the bottom up. The player's hit reactions to the Vanguard's blows went through our walking and physics model and stayed within a few millionths of a metre of the game. The Vanguard's attack shapes were placed through its skeleton the way the game does it, and its body was the first character to collide with the player in our model. A sound session decoded all 139 sound banks (3,295 clips) and predicted which footstep sound plays from the floor material in our collision map. Footsteps driven by our own simulated movement matched all 31 in the recording measured.

At the end of the window, the owner asked the session working on the attack logic how healthy the project was. Its answer was candid. The attack checker matched all 2,301 recorded decisions, but they came from one recording, one enemy and one map, which is strong evidence for that recording and weak evidence for the system. The suggested next step was another, different recording, not more checks on the same one. The owner agreed. The goal they restated in reply sums up where the project stands: "We are optimizing for a trustworthy independent Vanguard simulation, not generalizing every game subsystem."

The boss simulation that was dropped at 05:16 on day two is the goal again. This time it is built on parts we can measure.

From here on it gets technical: formulas, memory addresses and how each claim was checked.

What "bit-exact" covers here

The movement results are exact on the recordings they were checked against: walks, wall slides, turns and falls on the Vanguard's map. Some inputs are still taken from the game and labelled as such: the camera's heading, and the order in which Havok's broad first pass lists nearby objects. The game used as the reference is the recompiled port, not a real PlayStation 3. Anything that might be a quirk of the port stays marked until it is checked against an emulator or the console.
