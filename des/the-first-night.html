The first night: manipulate it, or cancel

Demon's Souls, the journal, part 2 · revised 2026-11-04 · draft

In short

Reading the game is one thing. Checking that you read it right means watching the real game run, and that is where the work slowed to a crawl.

We were treating the recompiled game like a sealed console, watching it from outside. The owner called that out at 02:53: "I think the approach is wrong."

Two hours later came the low point: "we find a way to manipulate the game, or we cancel the whole project." A four-minute test found the way. Then the owner dropped the boss simulation and set a much bigger goal.

How it went

Watching from outside

To check anything, we had to watch the real game run. The tools built that night were each reasonable on their own:

  • a watch that reports when the game reads a chosen memory field;
  • a way to run the game without a window and feed it controller input from a file;
  • a patch to skip the boot logos;
  • a live channel for reading, writing and freezing memory while the game runs.

Watching a game's memory

Everything a game knows at a given moment sits in its memory as numbers: the player's health, the boss's position, which attack it is in the middle of. Each value lives at a fixed spot, an address.

To learn what a value means, you watch it. Which part of the program reads the boss's health? What changes when it starts an attack? A "watch" asks the running game to report every time a chosen address is read or written. "Freezing" a value pins it, so you can see what the game does when, say, health never drops.

It works, but it is indirect. You learn about the program by watching what it leaves behind in memory, like studying an animal from its footprints.

Why it was slow

Each run spent about 45 seconds booting and loading a save before it could answer one small question.

The tutorial has no save points of its own, so getting anywhere near the boss took minutes.

The first enemy we picked to study never attacked at all, however much it was provoked. The owner checked that in their own play: it was simply that kind of enemy.

Hardware trouble that night forced every run and build to be throttled as well.

"I think the approach is wrong"

At 02:48 the owner asked how this was expected to go. The honest answer was "weeks".

Five minutes later:

I think the approach is wrong

And then the point that set the course for everything after:

to me it is absurd that this is proceeding slower than full black box decomp work we've done using emulators.

They were right. We had a C program we compile ourselves, and we were treating it like a sealed console, one memory field at a time.

Outside and inside

With an emulator, the game is a sealed box. You can look at its memory and press its buttons, but the program itself is the original machine code, which you can only observe.

A recompiled port is different. The program is source code on our own disk. We can add a line that prints something whenever a function runs. We can stop it at any point with ordinary programming tools. We can even swap out one function for our own.

Working from the outside of a program you hold the source of is like reading a book through the window of the shop that sells it.

Working from inside

Things changed within the hour.

First, a real debugger. The build got a symbol file, so an ordinary Windows debugger could stop inside any game function by name.

Then the owner suggested the step that mattered most:

we need to load a custom dll with the game, so we have a hook to load our code without recompiling every time

A full game build takes a long time, and from then on each one needed the owner's approval. Plugins needed neither.

The first plugin unlocked the game's own hidden debug menu. That menu can start the Vanguard's map directly, with no save at all.

Debuggers, symbols and plugins

A debugger is a programmer's tool that can pause a running program at a chosen spot and show everything it is holding at that moment. To pause "in the function that picks an attack", the debugger has to know where that function is. A symbol file tells it: a list of every function's name and location. Our build could make one, because we compile it ourselves.

A plugin is a small separate program file that the game loads when it starts. It runs inside the game, so it can read and change anything the game can. Rebuilding the whole game took a long time. A plugin takes seconds to build, and the game itself stays untouched.

A debug menu is a tool the original developers left inside the game for their own testing: jump to any map, change settings, skip ahead. Players never see it, but it is often still in the finished program.

The question nobody asked

The next hour taught a lesson about who knows what.

We spent it trying to work out how saving works, and how close you must get before the Vanguard wakes up. The owner knew both answers from playing:

  • a save always puts you back at the start of the area;
  • bosses have no wake-up range: the fight starts when you walk through the fog gate.

why don't you just ask me? we just went on a multi hour quest for info I can get you in 2 seconds flat

That has been a standing rule since. Facts about how the game behaves come from the player first. Only the mechanisms behind them are traced in the code.

What versus how

Finding out what a game does and how it does it are different jobs.

"Does the boss wait for you to come close?" is a what question. Anyone who has played the game knows the answer. "Which numbers in memory decide when the fight starts?" is a how question, and only the code can answer it.

Tracing code to answer a what question is like reverse-engineering a lift to find out which floor the café is on, when you could ask the receptionist.

A simulation nobody could use

The simulation got built anyway, with every unchecked value named as a stand-in for later tuning: a guess, marked as a guess, kept in one place so it can be corrected when the real value is known. Its attack choices matched the real odds from the code within about half a percentage point.

Then, at 05:01:

if its headless what use is it to me?

Five in the morning

At 05:06:

two options: we find a way to manipulate the game, or we cancel the whole project

The obvious way to manipulate it was teleporting the player, and that had failed earlier. Long jumps had left the player stuck in fog, and the guess was that that part of the map hadn't loaded yet.

The owner didn't accept the guess:

try warping around the map, test well make sure the problem we imagine is actually there, or isn't. then we'll call the shots

Why teleporting can break a game

Big 3D games don't hold the whole world in memory at once. They load the area around the player and keep loading more as the player moves, a technique called streaming. Walking, you never notice: the next room is ready before you arrive.

Teleport the player far away, and they may land somewhere that hasn't been loaded yet: no floor, no walls, nothing to stand on. The fear was that this would make teleporting useless for reaching the boss.

Four minutes

The test took four minutes.

Starting from the debug menu instead of a save, four long jumps across the Vanguard's map all landed cleanly. The last one went straight into the arena: the boss's health bar on screen, the player already knocked down.

The fight could now be reached in about a minute, on demand. The imagined problem wasn't there.

The new goal

At 05:16 the owner changed the target. They didn't care about the simulation; they had only picked it because it seemed easy.

we need to leverage this cheat engine to make progress into understanding this game. we eventually want to be able to reproduce all its functionalities one by one instead of running the original code through a translation layer of sort.

where do we start. what gives you leverage

Within ten minutes the goal was written into the project's instructions: reproduce the game piece by piece, without the PlayStation's concepts. The task at hand was to find out how hard that would be.

Running the original versus rebuilding it

The recompiled port still runs the original program, translated. Everything PlayStation-shaped is still in there: the memory layout, the helper cores' little programs, the way the graphics chip is driven. The port pretends to be a PS3 for the game's sake.

Rebuilding means writing our own code that does what the game does, system by system, until no translated PS3 code is left. Each piece we write can be run next to the original and compared, number for number. That is the long road, and the one this workspace prefers.

First measurements

Two quick measurements followed:

  • a static pass looking for clean boundaries between the program's parts;
  • a CPU sample of the Vanguard fight, to see where the time goes.

Neither gave a simple answer, and a later pass corrected the first sample's labels. The next article picks up from there.

From here on it gets technical: formulas, memory addresses and how each claim was checked.
