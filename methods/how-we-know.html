How we know what we know

Method, part 1 · revised 2026-10-23 · draft

In short

A game disc holds the game's program as machine code: millions of tiny instructions for the console's processor, unreadable to people. We turn that back into something readable, work out what each part does, and then test our understanding in the running game. Every claim on this site carries a label saying how far it got:

  • measured: we predicted a number from the program, then saw exactly that number in the running game.
  • in the code: it follows from reading the program, but hasn't been tested yet.
  • our reading: our interpretation, usually of why the designers did something. Reasoned, not proven.

How it works

Reading the program

A tool called a decompiler (we use Ghidra) turns machine code back into something close to the C language the game was originally written in. What comes out has no names: thousands of functions called things like FUN_8002d078, working on memory addresses instead of named values. The work is to read them one by one and give them names: this one is the damage formula, that number in memory is the player's strength.

Predicting

Once a piece of code is understood, it makes predictions. If the damage formula reads the way we think, then a Short Sword with 20 STR should do exactly 20 damage to a particular monster, and exactly 10 if the swing gauge is half full.

Checking

We then run the original game in an emulator (Mednafen) that our scripts can control. A check sets up a real situation in the game, such as walking up to a real monster or equipping armour through the real menus, and changes only the one value under test. The emulator stops at the right moment (a breakpoint) so the script can read what the game actually computed. If the game's number equals the predicted number, the claim is marked measured.

We don't use other players' findings as proof. Where a fan guide or a wiki says something different, the article says so, and says which version the game's own code supports.

From here on it gets technical: formulas, memory addresses and how each claim was checked.

The details

  • Corrections are public. When a finding turns out wrong, the article is revised, and its revised date and the Recently updated page show it. The research notes keep the dated correction.
  • The game itself is not here. Nothing on this site comes from the disc in bulk: no ripped files and no full data tables. What appears is the kind of thing a game guide prints: rules, formulas, item effects and short examples.
  • Our tools. Decompilation with Ghidra; runtime checks with a modified Mednafen driven by Python scripts. Each article's research notes are listed at its foot. The project's repository is not public yet.
