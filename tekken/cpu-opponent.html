How the computer chooses its moves

Tekken, read from the code, part 1 · revised 2026-11-04 · draft

In short

When you fight the computer in Tekken, it plays by your rules. It doesn't move its fighter directly. Instead it produces controller input, the same directions and button presses a player would make, and that input goes into the same place yours does. From there the game treats both fighters the same way.

Every other frame, the computer makes a new decision. It looks at the situation (how far away you are, whether you are attacking, whether a hit is about to land), lists the moves its fighter could start at that exact moment, sorts them into groups, and picks one using random numbers. The dice are tilted by the difficulty setting, by a strength level that depends on the opponent, and by how the two life bars compare.

We rebuilt this decision-maker and ran it beside the real game. Over more than 170,000 decisions, covering all 17 characters and every difficulty, it produced exactly the same controller input as the game every time measured.

How it works

A controller, not a puppet

Each fighter has a short memory of recent input: the last 60 frames of directions and buttons. The part of the game that turns input into moves (a punch, a throw, a sidestep) reads only that memory. For a human player, the memory is filled from the controller. For the computer, it is filled by the decision-maker in the code.

So a computer fighter can only do what a player could do with the same presses at the same moment. If a move needs a forward-forward-punch, the computer has to enter forward, forward, punch. This is also how the attract-mode demos work: when the game plays itself between title screens, both fighters are computer-controlled through exactly this path measured.

Two frames per thought

The decision-maker runs once per frame for each computer fighter. On every second run it thinks again. On the run in between, it keeps holding the direction it chose last time in the code. A few situations skip thinking entirely: while the fighter is in certain states, the computer either presses nothing or plays a fixed pattern of presses in the code.

What it can choose from

A thinking step first describes the situation in a few numbers: a distance class, whether the opponent has just started something new, whether a hit is coming and how soon, and whether the opponent is blocking or far away in the code.

Sometimes the answer is simple, and the computer just walks forward, walks back, or does nothing. Otherwise it builds a list. Every move in Tekken is part of a web of links like "from here, these inputs lead to these moves, but only between these frames". The computer collects every link that is open right now: up to 100 options, each one exactly the input a player would have to make in the code.

Sorting and rolling

Next, up to 16 filters go over the list. Each filter picks out the options that pass its own test. What each test favours hasn't been worked out in plain terms yet. Each filter adds the options it likes to its own group, so the groups are like shelves from most to least wanted in the code. Which filters even run depends on what the opponent is doing and on a dice roll against a value that differs per difficulty and level in the code.

Then the computer chooses:

  1. It rolls for a shelf. The roll is shaped rather than flat, so some shelves come up more often than others in the code.
  2. If that shelf is empty, it moves down to the next one until it finds options in the code.
  3. It picks one option on that shelf with another roll, and the input of that option becomes this frame's "controller" in the code.

What makes it harder

Every computer fighter carries a small record of settings that decide how the dice are tilted: thresholds for its rolls, a few limits and timers, and how much it may chain together. Which record is used depends on two things in the code:

  • the difficulty option, five steps (the game starts on the second one), and
  • a strength level from 0 to 8. In the arcade mode each opponent comes with its own level. In the attract demos the level is rolled anew at random, between 4 and 8.

That gives 45 records in all. At level 0, the first four difficulty steps share the same record, so difficulty only starts to matter as the levels go up measured.

There is one more tilt. Many of the computer's rolls are scaled by the ratio between the two fighters' life bars, so it plays differently depending on whether it is ahead or behind in the code.

Each character also has its own short row of numbers that the decision-maker reads. The hidden boss Devil doesn't have a row of his own: he uses Kazuya's measured.

Shared dice

The computer's random numbers come from the PlayStation's built-in random number routine, not from a generator of the game's own. Only one other part of the game uses it: the routine that sometimes picks a sound for a fighter. Because both use the same sequence, a sound picked in one frame changes the computer's rolls in the next measured. To predict the computer exactly, you have to predict the sounds too.

Versus mode

In Versus mode both fighters are always people. The mode never hands a fighter to the computer, and nothing in a Versus fight reads the difficulty setting in the code.

From here on it gets technical: formulas, memory addresses and how each claim was checked.

The details

The decision chain

Per fighter and frame, the input routine reads the fighter's input source: pad 1, pad 2, none, or computer. For the computer it calls the AI, which returns a pad word (four direction bits, four button bits). A recorder then turns the pad word into one byte in the fighter's 60-entry input ring: a direction 1–9 (numpad layout) from a lookup table, plus the newly pressed buttons in the code. The move engine reads only the ring in the code.

The AI keeps its own state per fighter, rebuilt at the start of every round: a round counter, the round timer at round start, the last pad word, the chosen difficulty record and the two per-character rows (own and opponent) in the code.

One thinking step

  1. In a special fighter state with a pattern flag: the pad is a fixed pattern from two small tables, pressed once every d* calls, where *d is the record's divisor (2 to 25); otherwise 0 in the code.
  2. In another blocking state: pad 0 in the code.
  3. Otherwise read the situation; on odd calls hold the last direction bits; on even calls decide in the code.
  4. A decision either returns a walk or no input directly, or builds the candidate list: every transition in the current move's list whose frame window contains the current frame and whose extra condition holds, at most 100 in the code.
  5. Up to 16 filters mark candidates with a level number and append them to a shared list; which filters run depends on the opponent's state, a percent roll against the record's threshold, and a second roll (rand >> 3) & 7 through a jump table (0–2: filter A, 3–4: A and B, 5–7: B) in the code.
  6. The pick: a level from a shaped roll (through a table of trigonometric values), a downward search for a non-empty level, then rand() × count >> 15 into that level's entries. The chosen transition's input word is the pad word in the code. When the per-level count table runs out, the original keeps reading down through memory past it; our copy reads the same memory, so it makes the same pick measured.

The percent roll and the life ratio

The percent roll draws 0–10,000 and scales it by the life ratio r* = opponent's life × 100 ÷ own life (100 when own life is 0). The roll is multiplied by 100 and divided by a number that depends on *r, and it is never less than 1 measured:

The steps aren't in order: when the opponent has at least twice the computer's life, the roll is left as it is, the largest it can be measured.

Random numbers

The BIOS rand(): seed ← seed × 1,103,515,245 + 12,345, result = (seed ÷ 65,536) mod 32,768 measured. It has exactly two callers in the game program: the AI and the per-fighter sound pick, which runs after both fighters' input in each frame, at most once per frame measured.

Difficulty records

5 difficulty steps × 9 levels = 45 records of 116 bytes. They hold three percent thresholds for the situation check, two values that grow with level, a limit on sequences, a threshold of 500 to 4,000 for the percent roll, two percentages of 50–100 that scale one of the AI's values, the pattern divisor (25 down to 2), and a bound of 1 to 10 on one counter measured. A flag for scripted motion sequences is 0 in all 45 records, so that code path can't run in arcade or Versus play measured.

Level: in the attract demos, 4 + (a roll of 0–8, halved) = 4 to 8; otherwise the opponent's level from the arcade table, at most 8 in the code.

How it was checked

The lab's model of the AI runs beside the game in the Mednafen emulator. At every call it is given the same game state and compared with what the game stores: the pad word, the ring byte, and the random seed afterwards measured.

The random seed was identical after every single call, so the model draws as many numbers as the game, in the same order measured. To run the computer for any pair of characters, the test sets both fighters' input source to "computer", which the game itself never does in Versus mode. Only the AI's own behaviour is the game's. A few branches no run reached (an attack-state check in the situation reading, a few filter lines, the 100-entry cap) are read from the code but not yet seen in action in the code.
